# Как устроен журнал

Готовое меню запускается командой из RUN.md. Оно экономит время на вводе, но не решает, права ли модель. Все данные записываются в src/results.db. Эту базу нужно сдать вместе с кодом.

## Порядок работы

Сначала создай случай с ожидаемым поведением и доказательством. Затем добавь точную формулировку. Получив ответ модели, создай попытку. После разбора добавь оценку. Номера каждой новой записи выводятся в терминале.

Для устойчивости добавь две формулировки одного случая, по попытке на каждую, затем создай пару и оцени пару. Не записывай одну пару повторно в обратном порядке.

Для длинного текста можно вставить сразу несколько строк. Отдельная строка :::END::: заканчивает ввод. Не вставляй её внутрь ответа. При прерывании незавершённая запись не сохраняется; предыдущие записи остаются.

## Таблицы для своего отчёта

| Таблица | Что хранит |
| --- | --- |
| dimensions | Пять заданных названий сторон качества |
| cases | Цель, вид и ожидаемый результат случая |
| prompts | Точные версии вопроса в рамках случая |
| attempts | Полный ответ, условия, контекст и результат SQL |
| pairs | Два ответа для проверки устойчивости |
| assessments | Ручную оценку ответа или пары и её причину |
| notes | Разминку, свои правила, наблюдения и выводы |

Точная схема — data/journal_schema.sql. Её можно читать, но менять выданный файл не нужно.

Связи: cases.dimension_id указывает основной dimension; prompts.case_id — случай; attempts.prompt_id — формулировку. В assessments заполнен либо attempt_id, либо pair_id. Если заполнен pair_id, dimension всегда stability. Для одной цели и одного dimension хранится одна текущая оценка.

kind в cases бывает normal, challenge или pair. phase в attempts бывает main, peer или defense. В отчёте основной результат считай по main. Обмен и исправление показывай отдельно, если они есть. Для пары обе попытки должны быть из одного случая, одной модели и одного этапа; сопоставимость остальных условий проверяет человек.

label в prompts: original — исходная формулировка, paraphrase — тот же смысл другими словами, shortened — сокращённая версия. Для повторного запуска не создавай новую формулировку: добавь попытку к прежнему prompt_id.

Модель и условия вводятся человеком. context_text в основных попытках берётся из выданного файла. Для этапа defense нужно вставить весь изменённый контекст. Содержимое ответа хранится в response_text, SQL модели — в model_sql, вывод выполнения — в execution_result.

## Что не перепутать в отчёте

Один случай может иметь несколько формулировок и много попыток. У одного ответа может быть несколько оценок. После соединения этих таблиц нельзя считать все строки как «число ответов»: один ответ может повториться.

Устойчивость считается по парам. Остальные стороны — по отдельным ответам. Не складывай их знаменатели в один процент.

Обычные и трудные случаи показывай отдельно. Повтор исходной формулировки и её сокращение тоже не смешивай. Не объявляй пустую группу успешной.

Запиши формулы до написания отчёта. Для доли ошибок используй только pass и fail, отдельно покажи unclear и na. Неокруглённая доля должна вычисляться как дробное число, а не целое деление.

## Исправление записи

Сохранённый ответ модели не переписывай. Если вставил не тот текст, добавь верную попытку и заметку с номерами обеих записей; объясни в отчёте, как исключил ошибочную запись ввода. Это не способ удалять неудобные ответы.

Случайную ошибку в оценке можно исправить пунктом меню 8. Старая оценка и объяснение сохраняются в notes, новая становится текущей. Если меняется само правило оценивания в бонусе, сохрани переоценку отдельной заметкой и не переписывай исходные оценки.

Если готовое меню не нравится, можешь сделать своё на Python. Сохрани схему и записи. Для вставки произвольного текста используй параметры SQLite: ответ модели может содержать кавычки и SQL, но должен храниться как текст, а не исполняться.
