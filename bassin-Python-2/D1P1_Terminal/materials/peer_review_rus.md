# Пир проверяет пира: полный порядок без сети

## 1. Принять и зафиксировать версию

Проверяющий отдельно распаковывает `Day01_participant.zip` в каталог, в котором НИКТО не решает задания. Это доверенная копия условий и инструментов. Её `START_HERE.md`, README, check-list, tools и datasets являются источником проверки. Не запускай инструменты из сдачи автора вместо этих файлов.

Пусть рядом с этой чистой папкой лежит полученный `day01_submission`. Из корня чистого `D1P1_Terminal`:

```bash
python3 tools/day1.py intake ../day01_submission --out ../review_peer
```

Папка проверки должна быть новой. Команда локально клонирует `develop` из bundle, фиксирует commit и сравнивает ВСЕ исходные файлы с чистым комплектом. Единственное ожидаемое изменение выданного файла — `src/partner/memory.txt`. Проверяется и история: запрещённое изменение с последующим откатом тоже видно.

В `review_peer/submitted` находится сданная работа, в `receipt.json` её версия, в `integrity.json` расхождения. Если отсутствует develop или bundle не открывается, зафиксируй проблему и не подменяй её произвольной папкой автора. Несовпадение байтов или состава оценивается в пункте 01; доказанная подмена уже принятой сдачи — отдельный флаг. Отсутствующий бонус ошибкой комплектности не является.

## 2. Прочитать и выполнить

Сначала просмотри сдаваемые скрипты. Затем из чистого комплекта:

```bash
python3 tools/day1.py verify ../review_peer
```

Команда запускает все случаи `datasets/cases.json` отдельными процессами, сравнивает точные stdout, stderr и код возврата, показывает историю и проверяет исходный бонус, если он есть. Зависший процесс отмечается отдельно. Вывод тестов — факты, не автоматическая оценка. Подробности находятся в `evidence.json`.

То же правило действует в заданиях: `probe` печатает каждое расхождение отдельной строкой. Смотри на список расхождений, а не на долю совпадений — часть проверок совпадает и у решения, которое не меняли вовсе. Хотя бы одно расхождение означает, что задание не выполнена.

Проверь `quest1.sh`, `errors.md`, `HOWTO.md` и необязательный `quest6.sh` по ЧЛ. Пустые или бессодержательные коммиты не доказывают этап работы. Для истории полезны команды из папки submitted:

```bash
git log --graph --oneline --all day01-start..develop
git log --format="%h %s" day01-start..origin/feature/first-scripts
git show ХЕШ_КОММИТА
```

Вторая команда показывает и общих предков feature-ветки после стартовой метки. Не требуй префикса у более раннего коммита задания 1 в develop. В графе найди точку ответвления и два последующих коммита feature. У merge должно быть два родителя, второй ведёт к сданной feature-ветке. Время между коммитами не оценивается.

## 3. Выдать практику по одной карточке

Локальные справочники и чтение своего кода разрешены. Проверяющий не диктует решение, не передаёт готовые фрагменты и не оценивает скорость печати. Условия и интерфейсы можно уточнять.

Каждый номер запускай только когда дошли до него. Начни с 4 и 5 — они различают самостоятельную работу лучше остальных, — затем возьми задание из 1–3. Пример:

```bash
python3 tools/day1.py card ../review_peer --part 1
```

Повтори для остальных, а при сданном бонусе — 6. Команда создаёт `cardN.json` и отдельную `practiceN`. Для Задания 1 там уже повреждены данные. Для 6 уже создан новый дамп. Конкретные параметры генерируются после приёма сдачи. 

Автор читает задание и до запуска объясняет предполагаемое поведение. Затем сам редактирует данные/код, выполняет команды, проверяет результат и объясняет выбранную пиром строку. При неудаче он может свериться со справочником, найти причину и повторить попытку на той же карточке. Это обучение, а не проверка на память.

После действий автора, из чистого комплекта:

```bash
python3 tools/day1.py probe ../review_peer --part 1
```

Подставь соответствующий номер. Результаты сохраняются отдельно. Для Задания 5: пир наблюдает воспроизведение и сам исполняет HOWTO в ещё одной пустой папке. Намеренную старую ошибку автор создаёт только в practice5; этот traceback не переносится во флаг CRASH.

Для Задания 6 дополнительно измени название выходной папки в команде запуска и попроси повторить прогон. Путь к дампу и выходной путь передавай отдельными аргументами в кавычках. Последняя строка — фраза карточки, `message.txt` содержит её же, выходная папка содержит только необходимые фрагменты.

Если автор показывает только готовый результат, а действия и объяснение не выполняет, соответствующая практика не подтверждена. Автотесты и заранее подготовленный универсальный скрипт не заменяют наблюдаемую работу с конкретной карточкой. Не обвиняй в списывании только за растерянность или ошибку.

## 4. Оценить и сохранить след

Скопируй `templates/review.md` в каталог проверки как `review.md`. 
Отдельно запиши принятый commit, подтверждение самостоятельных действий и итог.
Сохраните исходный bundle и протокол. Автор получает копию протокола для начала следующего дня. Сдаваемый commit не меняется; практические исправления можно изучать отдельно.
